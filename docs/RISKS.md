## A. 技术实现风险

### 🟢 R1 — 战利品表内部结构无公开遍历 API ✅ spike 已验证

> **2026-09-11 spike 结论：可行。风险 🔴H → 🟢L**。详见 `SPIKE-REPORT.md` R1 章节。

- **性质**：技术 ｜ **阶段**：~~design（spike）~~ → dev
- **原描述**：定价机制的地基是读取每个掉落物的概率，但相关字段为 private，需 Mixin Accessor。
- **spike 实测结果**：
  - ✅ **`LootTable` 在 1.21.1 中是 record，`pools` 有 public accessor；`LootPool.entries()` 亦为 public** → 表结构遍历零成本，无需 Mixin
  - ✅ 必须 Mixin `@Accessor` 的仅 **7 个字段**（LootPool.rolls/bonusRolls、SingletonContainer.functions、EntryContainer.conditions、RandomChanceCondition.probability、RandomChanceWithEnchantedBonus.unenchantedChance、SetItemCountFunction.value、LootItem.item）→ **单文件 ≤ 60 行**
  - ✅ 全量扫描 84 张有效实体表：110 个 `item` 条目可定价，仅 6 个非 item 条目需特殊处理（1 tag + 2 loot_table 引用 + 3 empty）
  - ✅ 定价算法**单调性 110/110 通过**（越稀有越贵，零违反）
- **spike 中修正的 4 个算法缺陷**（每个都会在真机表现为「价格乱来」）：
  1. 线性反比 → 对数曲线（否则 epk ≤ 0.11 全部撞价格上限，稀有度无法区分）
  2. `uniform` count 需逐值 `clamp(≥0)`（否则凋灵骷髅煤炭 `uniform(-1,1)` 被误判零产出→定天价）
  3. `rolls` 可为分布对象（女巫 `uniform(1,3)`），当 float 读会崩
  4. entry `weight` 需按 `weight/total` 计算（女巫木棍 weight=2）
- **残留缓解措施**（仍需实施）：
  1. 抽象 `LootPriceProvider` 接口隔离版本差异（为 1.21.8/1.21.11 扩展留位）
  2. 解析失败降级为「该生物不可交易」并 warn，不崩游戏
  3. 零期望产出条目**必须标记不可交易**，不得定天价
  4. 保留 `price_overrides` 配置作为人工兜底

### 🟡 R2 — 给非村民实体注入交易能力，跨加载器机制不同 ⚠️ 原判断已推翻

> **2026-09-11 spike 结论：风险 🔴H → 🟡M，且推荐方案由 B 改为 A。** 详见 `SPIKE-REPORT.md` R2 章节。

- **性质**：技术 ｜ **阶段**：design（最小原型验证）
- **原描述**：原版交易 GUI（`MerchantMenu`）要求目标实现 `Merchant` 接口。给 `Mob` 注入接口在 Fabric 与 NeoForge 是两套机制，Architectury common 模块无法屏蔽。
- **spike 实测结果 —— 推翻了「方案 A 成本高」的原判断**：
  - ✅ **`Merchant` 是纯行为接口，无字段依赖**：11 个 abstract 方法全部是行为方法，无一需要访问 private 字段
    - `getTradingPlayer`/`setTradingPlayer` → 存一个字段
    - `showProgressBar` → `return false`（怪物无等级条）
    - `isClientSide` → `return level().isClientSide`
    - `overrideXp`/`overrideOffers` → 空实现
    - `openTradingScreen` → **原版有 default 实现，可直接复用**
  - ✅ **`MerchantMenu` 构造无障碍**：`(int, Inventory, Merchant)` 只需传一个 Merchant 实例；槽位常量 `PAYMENT1_SLOT`/`PAYMENT2_SLOT`/`RESULT_SLOT` 均为 **public**，无需 Accessor
  - ✅ **`MerchantOffer` 原版已实现 FR-2.4 的全部语义**：`uses`、`maxUses`、`demand`、`priceMultiplier`、`specialPriceDiff` 全部现成，6 个构造器重载中有一个直接可用 → **交易次数/上限/补货逻辑几乎零成本**
  - ✅ **有可照抄的参考实现**：`AbstractVillager` 直接实现 `Merchant`
- **修正后的方案对比**：

  | 维度 | 方案 A（注入 Merchant） | 方案 B（自建 Menu） |
  |------|----------------------|-------------------|
  | GUI 工作量 | **零**（复用原版村民界面） | 需自写 Screen |
  | 网络同步 | **零**（原版已有） | 需自写包 |
  | 交易次数/补货 | **零**（MerchantOffer 已有） | 需自己实现 |
  | 客户端必装 | 可能不必 | **必须** |
  | 跨端差异 | 接口注入方式不同 | MenuType 注册有统一 API |
  | 冲突面 | 较大（注入 Mob 基类） | 较小 |
  | **总工作量** | **显著更低** ✅ | 高 |

- **修正后的推荐：方案 A**
- **残留待验证**（design 阶段做最小可运行原型）：
  1. ⚠️ NeoForge 的 Mixin 接口注入是否需要 Access Transformer 配置
  2. ⚠️ 注入 `Mob` 基类 + 运行时判定，vs 只注入 38 个已适配目标类 —— 前者代码少但影响面大
  3. ⚠️ 客户端不装模组时能否正常交易（若能则是重要卖点，需在 R25 中一并确定）

### 🟡 R3 — 敌对生物的 AI 系统适配 ✅ 已量化（v3 修正）

> **2026-09-11 spike 结论：风险 🔴H → 🟡M。** 详见 `SPIKE-REPORT.md` R3 章节与 `spikes/r3-ai/neutralization_plan_v3.json`。

- **性质**：技术 ｜ **阶段**：design（策略抽象设计）
- **原描述**：Goal 系统与 Brain/Behavior 系统是两套完全不同的 AI 架构。

#### ⚠️ 两次判据修正

| 版本 | 错误 | 后果 |
|------|------|------|
| v1 | 把 `customServerAiStep` 当 Brain 标志 | 误判末影人/烈焰人/幻翼/卫道士/唤魔者/凋灵 |
| v2 | 把「默认在白名单」等同于「零工作量」 | **漏算 8 个生物的适配工作**（用户指出） |
| v3 | 二分法「不是 Brain 就是 Goal」 | 误判末影龙（实为第三类自有 AI） |

| 系统 | 判据 | 数量 |

| ② **Brain** | 覆写 `makeBrain()`/`brainProvider()` | **6** |

### 🟡 R4 — 交易期间实体走开导致界面异常

- **性质**：技术 ｜ **阶段**：design
- **描述**：原版村民有 `TradeWithPlayerGoal`，交易时会停止移动、面朝玩家。中立僵尸没有这个 Goal——玩家打开界面后僵尸继续游荡，走出交互距离，可能导致界面卡住、物品状态不一致，或界面关闭时槽位物品丢失。
- **影响**：核心交互体验受损，且有丢物品的实际风险（服务器上尤其严重）。
- **缓解**：交易开启时给实体加临时「静止 + 注视玩家」行为；距离超阈值时**服务端主动关闭界面并退货**（复用 FR-2.2 的退货路径）。

### 🟡 R5 — 特殊生物的机制与中立化/交易冲突

- **性质**：技术 + 设计 ｜ **阶段**：design（逐项决议）
- **描述**：多个生物有与「中立 + 可交易」直接冲突的原版机制：

| 生物 | 冲突点 | 建议处理 |
|------|--------|---------|
| **末影人** | 被玩家注视即敌对（专属 look 机制，非标准索敌）；且会随机传送，交易中传送走 | 中立化需额外抑制注视触发；交易时抑制传送 |
| **苦力怕** | `SwellGoal` 依赖 target；敌对后爆炸会**炸死正在交易的其他怪物**、破坏地形 | ✅ **爆炸不触发示警**（非玩家攻击）。但爆炸波及其他中立怪物时，那些怪物按新语义**也不会转敌对**（伤害源非玩家）—— 语义已自洽，仅剩地形破坏与误杀交易对象的体验问题 |
| **蠹虫** | 原版已有 `SummonSilverfishGoal` 群体唤醒机制 | ✅ **不再视为冲突**。本模组只负责中立→敌对的状态切换，敌对后行为交回原版 AI。原版群体唤醒是敌对状态下的正常行为，**不干预、不叠加、不禁用** |
| **史莱姆 / 岩浆怪** | 死亡分裂出新实体，交易状态（NBT）**不继承**；且体型不同战利品不同 | 明确小史莱姆是独立交易个体 |
| **恶魂** | 飞行且体积巨大，玩家几乎无法右键交互 | 事实上不可交易，需承认 |
| **溺尸** | 水下交易界面可用性；且有三叉戟稀有掉落定价问题 | 测试水下场景 |
| **幼年僵尸 / 骑鸡僵尸** | 骑乘状态下右键可能被载具交互抢占 | 交互优先级需处理 |
| **女巫** | 战利品表条目极多（各种药水材料），交易列表可能过长溢出 GUI | GUI 需支持滚动或截断 |
| **幻术师（Illusioner）** | 自然不生成但存在于代码中；不在白名单则会被中立化 | 决定是否列入白名单 |

- **缓解**：design 阶段对上表逐项出决议，写进 `02-design.md`；无法妥善处理的加入默认白名单并如实声明。

### ✅ R6 — 白名单是「排除清单」，默认波及所有 Mod 生物 —— **已关闭**

> **2026-09-11 用户决策关闭。** 改用「已适配列表 ∩ 非白名单」双重决策模型，风险从根源消除。

- **性质**：技术 + 兼容 ｜ **阶段**：~~design~~ → 已解决
- **原描述**：FR-1.5 的语义是「除白名单外全部中立化」，意味着任何添加敌对生物的 Mod（Mowzie's Mobs、Alex's Mobs、Cataclysm 等）的自定义 Boss 也会被中立化，可能算出荒谬价格或出现半中立半敌对的诡异行为。
- **关闭理由**：新模型下

  ```
  是否中立化 = (在已适配列表中) AND (不在白名单中)
  ```

  「已适配列表」是**代码能力边界**，只包含本模组实现并测试过的原版生物。
  **未适配的第三方 Mod 生物天然不在范围内，行为完全不变，无需任何配置。**
- **原缓解方案作废**：不再需要 `neutralize_modded_mobs` 开关
- **保留的后续工作（P2）**：提供 API 让第三方 Mod 主动注册进「已适配列表」（opt-in 模型）

### 🟢 R7 — 「不链式传播」的标记正确性 ⬇️ 降级

> **2026-09-11 降级 🟡M → 🟢L**：用户澄清仇恨语义后，触发面大幅收窄。

- **性质**：技术 ｜ **阶段**：dev + test
- **描述**：FR-1.3 要求单层示警。实现上需在实体标记「本次敌对来源 = 被示警」，且该标记必须在正确时机设置与清除。
- **★ 降级理由（用户 2026-09-11 澄清仇恨语义）**：
  - 示警**仅由玩家攻击触发** —— NPC 攻击、环境伤害、怪物内斗全部不触发，触发路径从「任意伤害源」收窄到单一路径
  - 仇恨**只锁定攻击者玩家** —— 不扩散到其他玩家或 NPC，不存在多目标传播的状态爆炸
  - 本模组**只负责中立↔敌对的状态切换**，敌对后行为交回原版 AI，不与原版群体机制叠加
  - 综合：原先担心的「雪崩式全场敌对」在新语义下几乎不可能发生
- **影响**：核心玩法正确性（仍需验证，但失控上限已大幅降低）
- **缓解**：`angerSource` 枚举（PLAYER_DIRECT / KIN_ALERT / NONE）；单测覆盖 4.0 格边界（3.9 生效 / 4.1 不生效）；真机验证 4 格内激怒、6 格外静止、混种群体只激怒同类、**铁傀儡攻击不触发示警**

### 🟡 R8 — 战利品表条件（condition）导致概率计算失真

- **性质**：技术 ｜ **阶段**：design
- **描述**：多个稀有掉落带 `killed_by_player` 条件（如僵尸掉铁锭/胡萝卜/马铃薯 2.5%），还有 `random_chance_with_looting`、`entity_properties`（如溺尸只在特定条件掉三叉戟）、`table_bonus`。若解析时忽略 condition 直接取概率，会算出与实际严重偏离的价格。
- **影响**：定价失真，玩家感知为「价格乱来」。
- **缓解**：明确定义「计算基准 = 玩家击杀 + looting 0」；对无法静态求值的 condition（依赖运行时上下文）采取保守策略并记录 warn；spike 阶段用 3~5 张真实表对照实测掉落率验证算法。

### 🟢 R9 — 与原版 `NeutralMob` 机制语义混淆

- **性质**：技术 ｜ **阶段**：design
- **描述**：原版已有 `NeutralMob` 接口（猪灵、蜜蜂、疣猪兽的记仇/冷却机制），自带 `remainingPersistentAngerTime`、`persistentAngerTarget` 与 NBT 持久化。自造一套冷却逻辑会与之重复甚至冲突。
- **★ 新语义下的额外优势**：本模组的仇恨语义（单一玩家触发、锁定单一玩家、可冷却回中立）**与原版 `NeutralMob` 高度吻合** —— `persistentAngerTarget` 本身就是单目标 UUID。复用而非自造的收益比原先评估更高。
- **缓解**：FR-1.4 优先**复用** `NeutralMob` 接口机制而非自造；Mixin 让目标生物实现该接口。
- ⚠️ **注意**：猪灵/疣猪兽**原本就实现** `NeutralMob`，对这些生物需检查是否与原版既有逻辑冲突（尤其猪灵的「穿金装中立」与群体报复机制）。

### 🟢 R10 — Mixin 与其他 Mod 冲突

- **性质**：技术 ｜ **阶段**：dev
- **描述**：本 Mod 需 Mixin 到 `Mob`、`LootTable`、`LootPool` 等高频类。修改怪物 AI 的 Mod（Zombie Awareness、Improved Mobs、Guard Villagers）会注入同一区域。
- **缓解**：Mixin 使用低优先级；避免 `@Overwrite` 改用 `@Inject` + cancellable；文档中列出已知不兼容清单。

### 🟢 R11 — Architectury / Loom / Stonecutter 版本咬合

- **性质**：技术 ｜ **阶段**：design

## B. 设计与平衡风险

### ✅ R12 —— 已关闭（非风险，属产品定位）

> **用户裁定（2026-09-11）：这不是风险点，是本模组的设计意图。**

- **性质**：设计意图（原误判为风险）
- **产品定位**：本模组是**面向种田/建筑玩家的和平主义玩法包**，明确的设计目标为：
  1. **保留**非和平模式的血量与体力（饥饿）构建机制 —— 不退化为 Peaceful 难度
  2. 使玩家**免于战斗**，但仍能通过和平手段获取原本必须击杀怪物才能得到的掉落物
  3. 通过**价格机制 + 补货机制**，使掉落物的获取**仍保有难度成本** —— 和平不等于免费
- **与 Peaceful 难度的本质区别**：原版 Peaceful 会移除生物、关闭饥饿伤害、断绝掉落物获取途径；本模组保留生物存在、保留生存压力、把「战斗」这一条获取路径替换为「交易」，而非删除。
- **处理方式**：在 Modrinth / CurseForge 模组说明中**开门见山声明**该定位即可，不作为风险管理项。
- **关联影响**：R13（稀有掉落可购买）与 R14（怪物农场取代刷怪塔）**仍然是风险**，因为它们关乎「获取仍有难度」这条设计目标能否成立 —— 定价与补货参数标定是本设计意图的实现手段，参数没调好就等于设计目标落空。

### 🟡 R13 — 稀有掉落可购买，破坏进度节奏

- **性质**：平衡 ｜ **阶段**：design
- **描述**：骷髅头颅（凋灵前置）、三叉戟、末影珍珠（末地前置）、恼鬼之首 —— 原本需要长时间刷怪，现在只需绿宝石。而绿宝石可通过村民交易近乎无限获取（纸/作物换绿宝石农场）。
- **影响**：玩家可在游戏早期跳过大段进度，通关节奏崩塌。
- **缓解**：FR-2.4 的单次产出上限 + 每日补货 + 次数上限已提供基础约束；`price_max` 上限需谨慎（若设 64，骷髅头颅也就 4 组绿宝石）；建议为「进度关键物品」预设 `price_overrides` 高价，或提供 `progression_safe` 预设配置。

### 🟡 R14 — 怪物农场取代刷怪塔，且更高效

- **性质**：平衡 ｜ **阶段**：design
- **描述**：玩家圈养 20 只僵尸，每游戏日收割一轮固定掉落，无需刷怪塔基建、无战斗风险、产出可预测。
- **影响**：削弱刷怪塔这一经典玩法的意义。
- **缓解**：承认这是设计取舍；补货周期与次数上限是唯一杠杆，需通过实际游玩标定默认值（不能凭空拍）。

### 🟡 R15 — 「严格同 EntityType」的反直觉表现

- **性质**：设计 ｜ **阶段**：test + 文档
- **描述**：按用户决策，僵尸不示警**尸壳、溺尸、僵尸村民**（不同 EntityType）。玩家直觉上会认为「都是僵尸」。同理骷髅不示警凋灵骷髅/流浪者/诡异铁锈骷髅。
- **影响**：玩家可能报为 bug。
- **缓解**：这是**明确的设计决策**，在文档与 Mod 描述中说明；若后续想改，加 `kin_group` 配置支持自定义族群定义（P2）。

### 🟢 R16 — 交易次数上限默认值未标定

- **性质**：平衡 ｜ **阶段**：design
- **描述**：用户定了单次产出数量与补货周期，未定「每笔交易可做几次」。当前暂用村民惯例 4 次。这个数字直接决定经济强度。
- **缓解**：design 阶段结合 R13/R14 一并标定；需实际游玩验证而非纯推理。

## C. 发布风险

### 🟡 R17 — 双平台审核与元数据差异

- **性质**：发布 ｜ **阶段**：release
- **描述**：CurseForge 首次上传需人工审核（可能数天），Modrinth 亦有审核流程。两平台的依赖声明格式、版本兼容标记、Markdown 支持范围不同。声明错误会导致玩家装到不兼容版本 → 崩游戏 → 差评。
- **缓解**：先发 Modrinth（流程快、API 友好）验证流程，再发 CurseForge；用 `minotaur`（Modrinth）+ `cursegradle`/CF API 做 CI 自动发布，避免手工填错；每个 jar 必须实测启动过。

### 🟡 R18 — 双端 × 多版本 = jar 矩阵与错装风险

- **性质**：发布 ｜ **阶段**：release
- **描述**：首发 1.21.1 × (Fabric + NeoForge) = 2 个 jar；若加 1.21.8/1.21.11 则 6 个。文件命名不清 + 平台版本标记不准 = 玩家错装。
- **缓解**：统一命名 `peaceandlove-<mcver>-<loader>-<modver>.jar`；`fabric.mod.json` / `neoforge.mods.toml` 中写死 MC 版本范围（不用宽松通配）；首发只放 1.21.1 减少混淆。

### 🟢 R19 — 图标与宣传素材的原创性

- **性质**：法律 + 发布 ｜ **阶段**：release
- **描述**：两平台都需要项目图标与封面图。**不得使用 Mojang 原版贴图**（如直接裁僵尸头像）。截图中包含游戏画面属于合理使用，但图标必须原创。
- **缓解**：图标自行绘制或使用明确 CC0/自有素材；记录素材来源与授权，写进 `CREDITS.md`。

### 🟢 R20 — MIT 与映射文件分发

- **性质**：法律 ｜ **阶段**：design + release

## E. 维护与流程风险

### 🟡 R22 — MC 版本迭代导致 Mixin 目标漂移

- **性质**：维护 ｜ **阶段**：长期
- **描述**：本 Mod 深度依赖 Mixin 到内部类（`LootTable`、`Mob` 的 goal 注册），这类内部结构在 MC 小版本间也会变。1.21.1 → 1.21.8 → 1.21.11 → 26.x 每次都可能需要重写解析层。
- **影响**：维护成本随支持版本数线性增长，单人维护易失控。
- **缓解**：Mixin 面积尽量小；版本差异全部收口到 `LootPriceProvider` / `NeutralizationStrategy` 两个接口的实现类；Stonecutter 管理版本分支；**明确只承诺维护有限版本**，在描述中写清。

### 🟢 R23 — 测试无法靠单测覆盖

- **性质**：维护 ｜ **阶段**：test-plan
- **描述**：AI 行为、示警半径、交易界面同步、多人竞态（场景 4）几乎无法用纯单测覆盖，必须实际开游戏验证，且多人场景需两个客户端。
- **缓解**：单测只覆盖纯逻辑（定价算法、配置解析、距离判定）；行为部分写**可勾选的真机验证清单**（沿用 magic-sushi 项目的验证纪律）；服务器场景用 dedicated server + 两个 dev client 实测。

### 🟢 R24 — CI 构建矩阵成本

- **性质**：维护 ｜ **阶段**：automate-test
- **描述**：多版本多加载器构建在 GitHub Actions 上耗时较长，Gradle 缓存配置不当会每次全量下载 MC 与依赖。
- **缓解**：`gradle/actions/setup-gradle` 缓存；PR 只构建 1.21.1，tag 时才全矩阵。

### 🟢 R25 — 服务端/客户端安装组合

- **性质**：技术 + 发布 ｜ **阶段**：design
- **描述**：GUI 在客户端。若只服务端装、客户端不装会怎样？若走原版 `MerchantMenu`（方案 A）则客户端可能无需安装；若自建 Menu（方案 B）则**必须双端安装**。这个结论必须在描述中写清，否则服主会踩坑。
- **缓解**：design 阶段随 R2 方案一并确定并记录；`fabric.mod.json` 的 `environment` 字段正确声明。

### ⚠️ 新规则引出的技术要求（R2 相关）—— 已撤销

~~「每种掉落物每天 1 次」不能直接用 `MerchantOffer.maxUses`，需在实体 NBT 上维护 `Map<ItemId, lastTradeDay>`~~

**2026-09-11 追加验证后撤销此设计。** 字节码实测确认：

```
maxUses = 1  +  每游戏日补货一次  ≡  「每天最多买到一次击杀的量」
```

`MerchantOffer` 已含 `uses`/`maxUses`/`resetUses()`/`isOutOfStock()`，
`Villager` 已含 `restock()`/`shouldRestock()`/`lastRestockGameTime`。
实体 NBT 只需存一个 `long lastRestockDay`，比原设想简单得多。

⚠️ 唯一注意：`Villager.restock()` 耦合了 gossip/demand/价格波动，不能直接调用，需自写精简版 `resetAllUses()`。
