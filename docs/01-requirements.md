## 1. 项目背景与目标

### 背景

原版 Minecraft 的敌对生物是**无条件敌对**的：玩家进入侦测范围即被索敌，交互方式只有战斗一种。玩家与「怪物」之间不存在任何非暴力通道，怪物身上的掉落物只能通过击杀获取。

### 目标

把「敌对」从生物的**固有属性**改为**行为状态**，并为怪物开辟一条和平的资源获取通道：

1. **中立化** —— 敌对生物默认不主动索敌，只在被攻击或同族示警时进入敌对状态
2. **可交易** —— 中立状态下的怪物可用绿宝石交易其掉落物，定价由战利品表掉落概率反推
3. **可逆** —— 敌对状态会随时间冷却回中立，一次误伤不永久断绝关系
4. **玩家选择权** —— 打或不打交给玩家，而非游戏强制

### 成功标准（业务层面）

- 玩家夜间可以在不点火把、不穿盔甲的情况下穿过平原而不被攻击
- 玩家可以通过交易获得所有原版怪物掉落物（含稀有掉落）
- 攻击一只僵尸后，附近 4 格内的僵尸一并转为敌对并追击（不再向外扩散）
- 逃离足够久后怪物冷静，可再次交易
- 在 Modrinth + CurseForge 双平台发布，支持 Fabric / NeoForge 双端，覆盖 1.21.x

## 2. 用户角色与场景

### 2.1 用户角色

| 角色 | 描述 | 关注点 |
|------|------|--------|
| 单人玩家 | 本地存档游玩 | 生存体验变化、交易便利性、平衡性 |
| 服务器玩家 | 多人服务器成员 | 交易同步正确、不因延迟丢绿宝石 |
| 服务器管理员 | 安装并配置 Mod | 配置项粒度、性能开销、与其他 Mod 兼容 |
| 模组作者（下游） | 想扩展本 Mod | API 是否可挂钩、能否注册自定义交易 |

### 2.2 核心场景

**场景 1：和平夜行**
- 角色：单人玩家
- 触发：夜幕降临，玩家在地表行走
- 步骤：僵尸在 3 格外注视玩家 → 不索敌 → 玩家路过 → 僵尸原地游荡
- 结果：玩家未受伤害，僵尸未消失

**场景 2：向骷髅买箭**
- 角色：单人玩家
- 触发：玩家右键点击中立状态骷髅
- 步骤：打开交易界面 → 显示「N 绿宝石 ⇄ 骨头」「M 绿宝石 ⇄ 箭」→ 玩家放入绿宝石 → 取出物品
- 结果：玩家获得箭，骷髅保持中立，该笔交易剩余次数 -1

**场景 3：群体仇恨（单层，不链式）**
- 角色：单人玩家
- 触发：玩家攻击僵尸群中的一只
- 步骤：被打僵尸转敌对并追击 → 一次性查询其 4 格内**同 EntityType** 生物 → 这些僵尸转敌对追击玩家 → **被示警者不再向外二次示警**
- 结果：一次攻击激怒一圈僵尸，但不会雪崩式扩散全场

**场景 4：交易中被打断（多人）**
- 角色：服务器玩家 A、玩家 B
- 触发：A 正与苦力怕交易，**B** 攻击该苦力怕
- 步骤：苦力怕转敌对，**仇恨锁定 B（不是 A）** → 服务端强制关闭 A 的交易界面 → 未完成的绿宝石退回 A 背包
- 结果：无物品丢失，界面正确关闭；**苦力怕追击 B，不追击 A**
- ★ 这是「仇恨不扩散到其他玩家」语义的关键验证点

**场景 5：稀有掉落定价**
- 角色：单人玩家
- 触发：玩家与凋灵骷髅交易
- 步骤：查看交易列表 → 骷髅头颅因掉落概率仅 2.5% 而标价极高 → 煤炭因概率高而便宜
- 结果：价格体系符合直觉，稀有物品昂贵

**场景 6：打了又和解**
- 角色：单人玩家
- 触发：玩家误伤一只中立僵尸
- 步骤：僵尸追击 → 玩家逃离 32 格外 → 静候 30 秒 → 僵尸清除仇恨回归中立 → 玩家返回可正常交易
- 结果：关系可修复

## 3. 功能需求

### FR-1: 敌对生物中立化

#### Story FR-1.1 — 移除主动索敌

- 作为**玩家**
- 我想要**敌对生物默认不主动攻击我**
- 以便**我可以选择和平地探索世界**

**验收标准：**
- Given 一只僵尸，玩家在其 16 格侦测范围内，僵尸未受任何攻击
- When 游戏运行 30 秒
- Then 僵尸始终不将玩家设为攻击目标，不朝玩家移动，玩家不受伤害

**实现约束：** 移除/禁用生物的 `NearestAttackableTargetGoal<Player>` 等主动索敌目标，保留 `RandomStrollGoal`、`LookAtPlayerGoal` 等空闲行为。

**优先级：** P0 ｜ **端覆盖：** 服务端权威

#### Story FR-1.2 — 受击回击（仅玩家攻击触发）

- 作为**玩家**
- 我想要**攻击怪物后它会反击**
- 以便**和平不等于无敌，战斗仍有风险**

**验收标准：**
- Given 一只中立僵尸
- When **玩家**对其造成任意伤害
- Then 该僵尸立即转为敌对状态，将**该攻击者玩家**设为目标并持续追击，行为与原版一致

**★ 触发源限定（用户 2026-09-11 明确）：**

| 伤害来源 | 是否触发本模组的状态切换 | 说明 |
|---------|------------------------|------|
| **玩家直接攻击** | ✅ 是 | 唯一触发条件 |
| **玩家投射物/TNT/宠物** | ✅ 是 | 取 owner 为玩家则视同玩家攻击 |
| 其他 NPC 攻击（铁傀儡、村民卫兵、其他怪物） | ❌ **否** | 完全交由原版机制处理，本模组不介入 |
| 环境伤害（摔落、岩浆、窒息） | ❌ 否 | 同上 |
| 怪物内斗（僵尸打骷髅） | ❌ 否 | 同上 |

**★ 仇恨目标锁定（用户 2026-09-11 明确）：**
- 仇恨**只锁定发起攻击的那一个玩家**
- **不扩散到其他玩家**（多人游戏中 A 打的怪不会追 B）
- **不扩散到 NPC**（不会因此攻击村民、铁傀儡、动物）

**实现约束：** 保留/强化 `HurtByTargetGoal`，但**加判定条件**：仅当伤害来源可归因于玩家时才切换中立→敌对。非玩家来源的伤害走原版逻辑，本模组不做任何额外标记。

**优先级：** P0 ｜ **端覆盖：** 服务端

#### Story FR-1.3 — 同族仇恨示警（4 格，单层，不链式，仅玩家攻击触发）

- 作为**玩家**
- 我想要**攻击一只怪物会激怒它周围的同类**
- 以便**攻击群体怪物有真实代价**

**验收标准：**
- Given 3 只僵尸位于被攻击僵尸的 4 格内，另有 1 只僵尸在 6 格处，全部中立
- When **玩家**攻击中心那只僵尸
- Then 2 秒内中心僵尸 + 4 格内 3 只共 4 只转为敌对追击**该玩家**
- And **6 格处那只保持中立**（不因被示警者的二次示警而转敌对）
- And 4 格内的骷髅**不受影响**（非同 EntityType）
- And **若中心僵尸是被铁傀儡打的，则不触发任何示警**（非玩家攻击）

**已确认语义（用户 review 通过）：**
- 「同族」= **严格同一 `EntityType`**（僵尸只示警僵尸，不示警尸壳/骷髅/村民僵尸）
- 「4 格」= 球形欧氏距离 4.0，以**被直接攻击的生物**为中心
- 「扩散」= **仅单层，禁止链式传播**。被示警转敌对的生物**不再**触发自己的示警查询

**★ 触发源限定（用户 2026-09-11 明确）：**
- 示警**仅在玩家攻击时触发**
- **NPC 攻击不触发示警**，也不做任何额外的仇恨标记
- 被示警的同族，其仇恨目标同样**只锁定该攻击者玩家**，不扩散到其他玩家或 NPC

**★ 与原版机制的边界（重要）：**
本模组的示警机制**只负责「中立 → 敌对」的状态切换**。生物进入敌对状态后，
其行为完全交回原版 AI，包括原版自带的群体机制（如蠹虫 `SummonSilverfishGoal`、
猪灵 `PiglinAi` 的群体报复）—— **本模组不干预、不叠加、不禁用**。

**实现约束：** 需在实体上标记「本次敌对来源为示警」的 flag，示警而来的敌对不得再次触发 `alertKin()`。

**性能约束：** 示警查询**仅在生物被玩家直接攻击时触发一次**（事件驱动，非轮询）；单次查询实体数上限 32。

**优先级：** P0 ｜ **端覆盖：** 服务端

#### Story FR-1.4 — 敌对状态冷却（可逆）

- 作为**玩家**
- 我想要**逃跑足够久后怪物冷静下来重回中立**
- 以便**一次误伤不会永久毁掉与该群体的关系**

**验收标准：**
- Given 一只已敌对僵尸，玩家逃离至 32 格外
- When 持续 30 秒（默认，可配置）未再受到伤害且未发现目标
- Then 僵尸清除仇恨，恢复中立，可再次交易
- And 若冷却期间玩家再次进入视野并**未攻击**，冷却**不重置**（不是「看到就重新记仇」）
- And 若冷却期间该生物再次受到伤害，冷却计时**重置**

**开放实现细节（design 阶段定）：** 冷却计时器存实体 NBT（跨存档保留）还是内存（重载即清）。建议存 NBT 保持一致性。

**优先级：** P0（用户确认可逆为必需）｜ **端覆盖：** 服务端

#### Story FR-1.5 — 生效范围：已适配列表 ∩ 非白名单（双重决策）

- 作为**服务器管理员**
- 我想要**指定哪些生物保持原版敌对**
- 以便**保护游戏核心玩法不被破坏，同时能按自己口味调整**

**★ 生效范围模型（用户 2026-09-11 决策，取代原「排除清单」模型）：**

```
某生物是否被中立化 = (在「已适配生物列表」中) AND (不在「白名单」中)
```

| 概念 | 性质 | 含义 |
|------|------|------|
| **已适配生物列表** `adapted_mobs` | **代码能力边界**（只读，随版本更新） | 本模组已实现并测试过中立化逻辑的生物 |
| **白名单** `hostile_whitelist` | **管理员配置**（可增可减） | 从已适配范围中排除，保持原版敌对 |

**这个模型同时解决了三个问题：**

1. **第三方 Mod 生物不再被误伤** —— 原「排除清单」模型下默认中立化*所有*敌对生物（含 Mod 生物），
   现改为**只作用于已适配列表内的生物**。未适配的 Mod 生物**天然不受影响**，
   无需 `neutralize_modded_mobs` 开关（→ 关闭 R6）
2. **未实现的生物有明确语义** —— 如末影龙 v1.0 暂缓实现，则**不进已适配列表**，
   管理员从白名单移除它也不会有任何效果（因为根本不在适配范围内），语义一致无歧义
3. **能力与策略分离** —— 「能不能做」由代码决定，「要不要做」由管理员决定

**v1.0 已适配生物列表（38 个）：**

| AI 系统 | 数量 | 生物 |
|---------|------|------|
| Goal | 32 | 僵尸、僵尸村民、尸壳、溺尸、僵尸猪灵、骷髅、凋灵骷髅、流浪者、沼骸、巨人、蜘蛛、洞穴蜘蛛、苦力怕、恶魂、烈焰人、女巫、史莱姆、岩浆怪、末影人、末影螨、守卫者、远古守卫者、幻术师、劫掠兽、蠹虫、潜影贝、幻翼、掠夺者、卫道士、唤魔者、恼鬼、凋灵 |
| Brain | 6 | 猪灵、猪灵蛮兵、疣猪兽、僵尸疣猪兽、监守者、旋风人 |

**⏸ v1.0 暂缓（不进已适配列表）：**

| 生物 | 原因 |
|------|------|
| 末影龙 `minecraft:ender_dragon` | 使用 `EnderDragonPhaseManager`（Phase 系统），非 Goal 非 Brain，需完全独立的适配方案。留待 v1.1 评估 |

**默认白名单（用户确认，6 项）：**

| 生物 | ID | 理由 |
|------|-----|------|
| 掠夺者 | `minecraft:pillager` | 袭击事件依赖其主动攻击村庄 |
| 卫道士 | `minecraft:vindicator` | 同上 + 林地府邸难度 |
| 唤魔者 | `minecraft:evoker` | 同上 |
| 恼鬼 | `minecraft:vex` | 唤魔者召唤物，中立化会让唤魔者失去威胁 |
| 幻翼 | `minecraft:phantom` | 主动索敌是其唯一存在意义 |
| 潜影贝 | `minecraft:shulker` | 末地城守卫，中立化会让末地城无难度 |

> 📌 这 6 个**均在已适配列表内**，管理员移出白名单后中立化逻辑会立即生效。
> 「默认排除」是策略选择，不是能力缺失。

**监守者：** 已适配且**不在**默认白名单（用户明确裁定），即默认会被中立化并可交易。

**凋灵：** 已适配（走标准 Goal 系统），不在默认白名单。但受 `boss_trading_enabled` 控制是否生成交易 offer。

**必须支持：**
- 白名单**可增可减**，接受任意 `EntityType` ID
- 白名单中若填入**不在已适配列表**的 ID（如 Mod 生物、末影龙）→ 接受配置但**不产生效果**，
  启动时以 `INFO` 级别提示「该生物不在适配范围内，白名单条目无实际作用」
- 提供命令或日志输出**查询当前已适配生物列表**，让管理员知道可配置范围

**未来扩展（P2）：** 提供 API 让第三方 Mod 主动注册自己的生物进「已适配列表」（opt-in 模型）。

**验收标准：**
- Given 默认配置
- When 玩家靠近掠夺者哨塔
- Then 掠夺者正常主动攻击玩家（原版行为）
- And Given 管理员将 `minecraft:pillager` 从白名单移除并重载配置
- Then 掠夺者变为中立且可交易（**因其在已适配列表内**）
- And Given 管理员将 `minecraft:zombie` 加入白名单
- Then 僵尸恢复原版主动索敌，且右键不打开交易界面
- And Given 管理员将 `minecraft:ender_dragon` 从白名单移除（或它本就不在白名单）
- Then 末影龙行为**完全不变**（**不在已适配列表内**），日志给出 INFO 提示
- And Given 服务器安装了添加自定义敌对生物的第三方 Mod
- Then 这些 Mod 生物行为**完全不变**，无需任何额外配置

**优先级：** P0 ｜ **端覆盖：** 服务端

### FR-2: 怪物交易系统

#### Story FR-2.1 — 中立生物可交易

- 作为**玩家**
- 我想要**右键中立怪物打开交易界面**
- 以便**用绿宝石换取它的掉落物**

**验收标准：**
- Given 一只中立僵尸，玩家空手或手持无交互行为的物品
- When 玩家右键点击该僵尸
- Then 打开交易界面，显示该生物的可交易物品列表

**交互优先级规则（design 阶段定，此处列出需处理的冲突）：**
- 玩家手持原版有交互行为的物品（如对僵尸村民用金苹果治疗、对疣猪兽用作物）→ **原版行为优先**
- 建议：**普通右键 = 交易**，**潜行右键 = 原版交互**（或反之，需在 design 定并写进文档）
- 手持食物/工具不应误触发交易

**优先级：** P0 ｜ **端覆盖：** 客户端（GUI）+ 服务端（逻辑）

#### Story FR-2.2 — 敌对状态禁止交易

- 作为**玩家**
- 我想要**敌对怪物拒绝交易**
- 以便**和平与暴力互斥，选择有意义**

**验收标准：**
- Given 一只已敌对的僵尸
- When 玩家右键点击它
- Then 不打开交易界面，执行原版右键行为
- And Given 玩家正在与某怪物交易，界面打开中
- When 该怪物转为敌对（被第三方攻击 / 同族示警）
- Then 服务端强制关闭界面，玩家已放入槽位的绿宝石全部退回背包，**无物品丢失**

**优先级：** P0 ｜ **端覆盖：** 服务端权威 + 客户端界面同步

#### Story FR-2.3 — 战利品表反推定价

- 作为**玩家**
- 我想要**价格反映掉落物的稀有度**
- 以便**定价符合直觉，不需要查表**

**验收标准：**
- Given 凋灵骷髅的战利品表（煤炭约 33%，骷髅头颅 2.5%）
- When 玩家打开其交易界面
- Then 骷髅头颅的绿宝石价格显著高于煤炭
- And 对任意两个掉落物，掉落期望值更低者价格更高（单调性）
- And 所有价格落在 `[price_min, price_max]` 区间内

**定价原则（算法细节交 design 阶段的 ADR）：**
- 输入：该 `EntityType` 战利品表中每个物品的**期望产出数量**（概率 × 数量期望 × rolls）
- 输出：绿宝石价格，与期望产出**成反比**
- 必须处理：价格上下限截断、`looting` 加成条目的处理策略（建议按 looting 0 计算）、非物品条目（经验、嵌套 LootTable、空条目）的跳过
- 必须支持：配置文件 `price_overrides` 手动覆盖（算法不可能对所有情况都合理）
- 计算时机：**数据包加载完成后一次性计算并缓存**

**技术风险（H）：** 战利品表内部结构（`pools`/`entries`/`conditions`/`functions`）无公开遍历 API，需 Mixin Accessor。1.21.x 内部各小版本亦可能有变动。→ 需抽象 `LootPriceProvider` 接口隔离版本差异。

**优先级：** P0 ｜ **端覆盖：** 服务端

#### Story FR-2.4 — 交易上限与每日补货

- 作为**服务器管理员**
- 我想要**单笔交易数量有上限且每天补货**
- 以便**玩家无法无限刷取，破坏经济平衡**

**已确认规则（用户 review 通过）：**
- **单次交易的物品产出数量** = 该物品**一次击杀的最大掉落数量**（取战利品表该条目的 `count` 上界，含 looting 上限？→ design 定，建议按 looting 0 的 max）
- **补货周期**：每游戏日一次（24000 tick），周期**可配置**
- 交易次数用尽后置灰，补货后恢复

**验收标准：**
- Given 僵尸的腐肉战利品条目为 `0-2`（一次击杀最多 2 个）
- When 玩家与该僵尸交易腐肉
- Then 单次交易产出 **2 个**腐肉
- And Given 该笔交易的次数已用尽
- When 玩家再次尝试
- Then 该笔交易置灰不可用
- And When 游戏时间经过 1 个完整日夜周期
- Then 该笔交易恢复可用

**待 design 明确：**
- 每笔交易的**可用次数**是多少？（用户只定了「单次产出数量」和「补货周期」，未定次数上限本身。建议默认值可配置，如 `max_uses_per_trade = 4`，与村民一致）
- 是否引入村民式「需求涨价」？→ **P2，暂不做**

**优先级：** P0（上限与补货机制）｜ **端覆盖：** 服务端

#### Story FR-2.5 — 交易数据持久化

- 作为**玩家**
- 我想要**怪物的交易记录在重进世界后保留**
- 以便**不能通过重登刷新交易上限**

**验收标准：**
- Given 玩家与某只持久化怪物（已命名/牵引/在加载区块内）完成部分交易
- When 玩家退出并重进世界，该实体未被卸载清除
- Then 该怪物的交易次数与补货计时保持不变

**注意：** 普通怪物会因区块卸载或难度重置消失。交易状态存于**实体 NBT**（随实体消亡），非全局存档。这是可接受的设计——玩家若想稳定交易需自行圈养怪物。

**优先级：** P1 ｜ **端覆盖：** 服务端

## 4. 非功能需求

### 4.1 性能

- **同族示警查询**：仅在生物被直接攻击时触发，单次范围查询实体数 ≤ 32，**无轮询开销**（不链式传播使总查询次数为 O(被攻击次数)，而非 O(受影响生物数)）
- **冷却检查**：每生物每 20 tick 一次，或用 tick 计数器递减（无范围查询）
- **服务端 TPS**：200 只中立生物同屏、20 只敌对的场景下，MSPT 增幅 ≤ 5ms（对比原版基线）
- **定价计算**：数据包加载时一次性完成并缓存，缓存构建耗时 ≤ 500ms；**禁止**在打开 GUI 时实时计算
- **内存**：定价缓存常驻 ≤ 2MB

### 4.2 网络与同步（多人核心）

- 所有状态变更（敌对/中立、交易次数、价格、补货计时）**服务端权威**，客户端仅渲染
- 交易界面复用原版 `MerchantMenu` 同步机制或等价自定义包
- **禁止信任客户端发来的价格/数量字段**
- 敌对状态按需同步至客户端（若做视觉提示），事件驱动
- 配置从服务端同步至客户端（价格显示需一致）

### 4.3 兼容性

| 目标 | 版本 | 加载器 | Java | 优先级 |
|------|------|--------|------|--------|
| Minecraft | **1.21.1** | Fabric + NeoForge 21.1.250 | 21 | **P0（首发）** |
| Minecraft | 1.21.8 | Fabric + NeoForge 21.8.54 | 21 | P1 |
| Minecraft | 1.21.11 | Fabric + NeoForge 21.11.45 | 21 | P1 |
| Minecraft | 26.1 / 26.2 | Fabric + NeoForge 26.2.x | 21+ | P2（后续） |
| ~~1.20.x~~ | — | — | — | **已放弃（用户决策）** |

**Mod 兼容性：**
- 与 EMI / JEI 共存无冲突（不注册配方，风险低）
- 对修改怪物 AI 的 Mod（Zombie Awareness、Improved Mobs 等）**明确声明不保证兼容**
- 对添加自定义敌对生物的 Mod：默认**不中立化**（白名单是反向的——只有已知敌对生物列表内的才中立化？还是全部中立化除白名单？→ **design 必须明确这个语义**）
  - ⚠️ 注意：FR-1.5 的 `hostile_whitelist` 是「排除清单」，意味着**默认所有敌对生物都中立化**，包括其他 Mod 的。这对兼容性有风险，design 需给出保守方案（如提供 `neutralize_modded_mobs = false` 开关）

### 4.4 可用性与降级

- 战利品表解析失败 → warn 日志，该生物**降级为不可交易**但中立化仍生效
- 配置文件解析失败 → 使用默认值启动并 warn，不崩游戏
- Mixin 注入失败 → **崩溃**并给出清晰错误信息（宁可崩也不要行为诡异）
- 白名单中含无效 EntityType ID → warn 并跳过该条

### 4.5 国际化

- 初始语言：`en_us`、`zh_cn`
- 所有面向玩家文本走语言文件，无硬编码

**核心架构决策（design 阶段 ADR，此处仅列选项）：**

1. **多加载器策略**：Architectury（common/fabric/neoforge 三模块）vs 各加载器独立源码树
2. **多 MC 版本策略**：Stonecutter 0.9.8（单分支预处理注释）vs Git 分支 vs 独立 subproject
   - 建议：首发只做 1.21.1，架构留好扩展位，1.21.8/1.21.11 用 Stonecutter 后补
3. **交易能力注入方案（R2，高风险）**：
   - 方案 A：Mixin 给 `Mob` 注入 `Merchant` 接口，复用原版 `MerchantMenu`（省事但 Fabric/NeoForge 注入机制不同，Architectury 无法屏蔽）
   - 方案 B：自建 `MenuType` + 自定义网络包（跨端一致性好，工作量大）
   - **必须 spike 验证**
4. **AI 目标改写方案**：Mixin 拦截 `Mob.registerGoals`/`targetSelector` vs 运行时移除 Goal vs 覆盖 `Mob.setTarget`
5. **战利品表访问（R1）**：Mixin Accessor 遍历 `LootTable.pools` → `LootPool.entries`，需处理各 `LootPoolEntryContainer` 子类型
6. **映射选择**：Yarn（Fabric 原生）vs Mojang Official（NeoForge 原生）→ Architectury 项目通常用 Mojang 映射统一
